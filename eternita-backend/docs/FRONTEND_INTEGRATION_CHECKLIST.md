# Frontend Integration Checklist and Manual HTTP Journey

Use this plan against a disposable Firebase project or Firestore emulator. It exercises current backend behavior; it does not assume beneficiary access to Firestore. Beneficiary reads must go through the API because [`firestore.rules`](../firestore.rules) denies direct reads of another user's records and denies client writes.

## Before testing

1. Start the backend with valid server-side Firebase Admin credentials and the Firestore target intended for this run. For the delayed death-report check, set `DEATH_REPORT_CONFIRMATION_DELAY_MINUTES` to a short staging value such as `0.05` (three seconds) before starting the backend. The poller checks about once per second. Restore the normal setting after the test. Do not point a short-delay test at production.
2. Configure the backend's `CORS_ALLOWED_ORIGINS` to the actual Expo web origin. Development defaults are exactly `http://localhost:8081` and `http://localhost:19006`; the frontend must tell the backend developer which origin it uses.
3. Obtain Firebase Web configuration from Firebase Console. For a new owner, call `POST /auth/register-owner` first; do not call Firebase client `createUserWithEmailAndPassword` before it, because the backend creates the Auth account and profile. Then sign in that owner through Firebase client Auth. Create/sign in a second Firebase Auth user for the beneficiary, then use its ID token to join. Create an optional third signed-in user for the unauthorized-beneficiary check.
4. Store ID tokens only in the local HTTP client's environment, never in source control, logs, screenshots, or this checklist. Set `ownerToken`, `beneficiaryToken`, `intruderToken`, `ownerUid`, `beneficiaryUid`, `beneficiaryHandle`, `entryId`, `privateEntryId`, `futureEntryId`, `policyId`, `inviteCode`, and `requestId` from responses as you proceed.
5. For AI steps, configure a valid server-side `GEMINI_API_KEY`. The test will fail at the provider step if the key is absent, invalid, rate-limited, or unreachable. Never put it in the Expo app.

### Standard headers

For every protected HTTP request below, send:

```http
Authorization: Bearer <Firebase ID token for the actor>
Content-Type: application/json
```

Do not send a client-supplied UID as authentication. `POST /auth/register-owner` is public. For authenticated calls, the guard uses the Firebase-verified UID. In the existing emulator integration tests, `x-test-uid` is a test-only mocked guard header; it is not a frontend contract.

### Fixtures and policy text

Use a unique owner email for each fresh run. Choose `beneficiaryHandle` as lowercase letters/digits/underscores, for example `maria_santos`. Create at least three entries by repeating the draft/edit/publish steps below:

- Permitted: title `Family memory`, tags `[`"family"`]`, no `releaseDate`.
- Denied by policy: title `Private memory`, tags `[`"private"`]`, no `releaseDate`.
- Date-gated: title `Future memory`, tags `[`"family"`]`, `releaseDate` set to a date after today's UTC date (for example tomorrow's UTC date).

Create the policy after the beneficiary has joined and requested access, using the beneficiary handle as the protocol name:

```text
protocol <beneficiaryHandle>:
  may read full of entries tagged family
  may not read full of entries tagged private
```

The date-gated entry is denied before its release date even though its tag matches the allow rule. Recheck it after its `releaseDate` (date-only values are parsed as UTC midnight) and after death release; it should then be available subject to policy. This requires testing across the configured date boundary; there is no clock-override HTTP API.

## Owner-beneficiary legacy journey

For each row, substitute the route variables established from earlier responses. Firestore verification is read-only inspection in Firebase Console, Emulator UI, or an approved Admin SDK tool. The backend intentionally has no client route for inspecting death-report documents.

| # | HTTP request, headers, and exact body | Expected status and response fields | Firestore state and pass/fail criteria |
|---:|---|---|---|
| 1. Owner registration | `POST /auth/register-owner`; no Authorization header. Body: `{"email":"<unique-owner-email>","password":"<valid-test-password>","displayName":"Test Owner"}` | `201`; `{uid,role:"owner",name,handle}`; role is `owner`. | `users/{uid}` exists with role/name/handle and defaults; `users/{uid}/activity/{id}` has registration event. Pass if both Firebase Auth user and owner profile are created. |
| 2. Firebase sign-in and ID token | Firebase client SDK sign-in for the registered owner; **no backend HTTP route**. Retrieve `await auth.currentUser.getIdToken()` (force refresh with `getIdToken(true)` if needed). | Firebase Auth succeeds and returns a non-empty ID token. | Firebase Auth account matches response `uid`. Pass if the token is available only to the client and can be sent to the API. |
| 3. Bearer token contract | `GET /auth/me`; standard headers with `<ownerToken>`; no body. | `200`; `{uid,role,name,handle,settings}` and `uid === ownerUid`. | No Firestore mutation. Pass if the verified token identity is used; missing/invalid/expired tokens should instead return `401` with `code:"UNAUTHORIZED"`. |
| 4. Owner creates a draft | `POST /entries`; standard headers with `<ownerToken>`. Example body: `{"title":"Family memory","originalText":"A permitted family memory.","journal":"Personal","entryDate":"2026-11-28","entryTime":"14:30","mood":4,"people":[],"tags":["family"],"isDraft":true,"writingMode":"verbatim"}`. For fixtures 2/3, use titles/tags described above and set `releaseDate` on the future fixture. | `201`; response fields: `entryId,ownerUid,title,originalText,journal,entryDate,entryTime,mood,people,tags,isFavorite,isDraft,writingMode,finalText,isHidden,currentVersion,previousHash,entryHash,createdAt,updatedAt`, plus `releaseDate` if sent. `isDraft:true`. | `users/{ownerUid}/entries/{entryId}` exists; draft is not in append-only sequence yet. Pass if saved values match and `isDraft` is true. |
| 5. Owner edits draft | `PATCH /entries/<entryId>`; standard headers with `<ownerToken>`. Body: `{"title":"Family memory updated","originalText":"An edited permitted family memory."}`. | `200`; `{entryId,currentVersion,updatedAt}`; `currentVersion` increases. | Draft entry fields are updated and a snapshot exists at `users/{ownerUid}/versions/{entryId}/versions/{versionId}`. Pass if the version snapshot and updated draft are present. |
| 6. Owner publishes entry | `POST /entries/<entryId>/publish`; standard headers with `<ownerToken>`; no body. | `201`; `{entryId,previousHash,entryHash,sequence,publishedAt}`. | Entry has `isDraft:false`, `sequence`, `publishedAt`, and hash fields; owner sequence/hash state updates. Pass if sequence is assigned and hash is non-empty. A later `PATCH` to the published entry should be `409`. |
| 7. Owner creates policy | `POST /policies`; standard headers with `<ownerToken>`. Body: `{"policyText":"protocol <beneficiaryHandle>:\n  may read full of entries tagged family\n  may not read full of entries tagged private"}`. | `201`; `{policyId,ownerUid,policyText,compiledFacts,version,status}`; status `active`. | `users/{ownerUid}/policies/{policyId}` exists and is active; any prior active policy is superseded. Pass if policy compiles and a current active policy is returned by the next check. |
| 8. Owner invites beneficiary | `POST /invites`; standard headers with `<ownerToken>`. Body: `{"handle":"<beneficiaryHandle>","name":"Test Beneficiary"}`. | `201`; `{inviteId,code,handle,name,expiresAt}`. Save `code` as `<inviteCode>`. | `invites/{inviteId}` has owner UID, code, pending status, expiry. Pass if a non-empty invite code and future expiry are returned. |
| 9. Beneficiary joins | First create/sign in the beneficiary's Firebase Auth account and obtain `<beneficiaryToken>`; then `POST /auth/join` with standard headers using that token. Body: `{"code":"<inviteCode>","name":"Test Beneficiary"}`. | `201`; `{uid,role:"recipient",ownerUid,name,handle}`. | `users/{beneficiaryUid}` has `role:"recipient"`, `ownerUid`, name and invited handle; invite status becomes used with `usedByUid`. Pass if profile is linked to the intended owner. |
| 10. Beneficiary requests legacy access | `POST /legacy/request`; standard headers with `<beneficiaryToken>`. Body: `{"ownerUid":"<ownerUid>"}`. | `201`; `{requestId,status,decision,decisionAt,activatedAt,revokedAt,createdAt,updatedAt}`; status `pending`. Save `<requestId>`. | `users/{ownerUid}/legacyRequests/{requestId}` has `requesterUid:beneficiaryUid` and pending status. Pass if request is pending and linked to the right actors. |
| 11. Owner approves request | `POST /legacy/requests/<requestId>/approve`; standard headers with `<ownerToken>`; no body. | `201`; safe request fields; status and decision `approved`, `decisionAt` populated. | Request document records owner as decision actor and approved state. Pass if a different user cannot approve it. |
| 12. Owner activates request | `POST /legacy/requests/<requestId>/activate`; standard headers with `<ownerToken>`; no body. | `201`; safe request fields; status `active`, `activatedAt` populated. | Request status is active. Pass if beneficiary access is now eligible for policy evaluation. |
| 13. Beneficiary views permitted entries | `GET /entries/<entryId>?ownerUid=<ownerUid>&access=full`; standard headers with `<beneficiaryToken>`; no body. Use family entry. | `200`; `{accessGranted:true,title,content,createdAt}`. Also verify summary/existence projections if the UI uses them. | No mutation. Pass if response includes only the requested projection and permitted content. Private and future fixtures should return `{accessGranted:false,message}`. |
| 14. Beneficiary asks AI | `POST /ai/ask`; standard headers with `<beneficiaryToken>`. Body: `{"ownerUid":"<ownerUid>","question":"What family memory is available to me?"}`. | `201`; on provider success `{answer,status:"success",error:null,citations,selectedEntryIds,accessLevels}`. | `users/{beneficiaryUid}/aiUseLogs/{id}` stores response status, selected IDs/access levels and prompt hash/length, not raw prompt text. Pass if status is success and the result has citations. |
| 15. AI returns only permitted records with citations | Inspect the response from step 14. | `201`, `status:"success"`; `selectedEntryIds` contains permitted family entry IDs only; `citations` contains citations for those selected entries; answer includes citation markers. | Compare selected IDs against owner entries and the policy. Private and not-yet-released entry IDs must be absent. Pass only if every selected ID is permitted and every selected entry has a citation; provider-generated wording itself is not deterministic. |
| 16. Unapproved beneficiary gets safe denial | Use a separate Firebase-authenticated user `<intruderToken>` not linked by an active/released grant. `GET /entries/<entryId>?ownerUid=<ownerUid>&access=full` and `POST /ai/ask` with body `{"ownerUid":"<ownerUid>","question":"Tell me about this diary."}`. | Entry route: `200` `{accessGranted:false,message:"Entry not available."}` for no grant. AI: `201`, `status:"denied"`, `error.code:"NO_ACTIVE_LEGACY_GRANT"`, empty `citations`, `selectedEntryIds`, and `accessLevels`. | No diary content appears in either response; AI log records denied status with no selected IDs. Pass if refusal is safe and no private fields leak. |
| 17. Owner revokes access | `POST /legacy/requests/<requestId>/revoke`; standard headers with `<ownerToken>`; no body. | `201`; safe request fields; status `revoked`, `revokedAt` populated. | Request is revoked. Pass if the owner succeeds and unauthorized actors receive 403. |
| 18. Revoked beneficiary loses access | Repeat step 13 and step 14 with `<beneficiaryToken>`. | Entry `200` `{accessGranted:false,message:"Entry not available."}`. AI `201` with `status:"denied"`, `error.code:"NO_ACTIVE_LEGACY_GRANT"`, empty selections/citations. | Revoked status is not an eligible grant. **To continue the death-report journey, create a fresh request and repeat steps 10–12**; this is necessary because report submission requires an active or released grant. Pass if access is denied before renewal. |
| 19. Owner freezes active policy | After renewing the request and reaching `active`, call `POST /policies/<policyId>/freeze`; standard headers with `<ownerToken>`; no body. | `201`; `{policyId,status:"frozen"}`. `GET /policies/active` returns `null`. | Policy status is frozen. Pass if owner can freeze it and an active policy is no longer returned. |
| 20. Beneficiary loses access under frozen policy | Repeat `GET /entries/<entryId>?ownerUid=<ownerUid>&access=full` and `POST /ai/ask` as beneficiary while grant remains active and policy is frozen. | Entry: `200` `{accessGranted:false,message:"No active policy is available for this owner."}`. AI: `201`, `status:"denied"`, `error.code:"NO_PERMITTED_ENTRIES"`, empty selections/citations. | Grant remains active but no active policy permits entry access. Pass if no raw entry content is returned. |
| 21. Beneficiary submits death report | While grant status is still active (even though policy is frozen), `POST /legacy/death-reports`; standard headers with `<beneficiaryToken>`. Body: `{"ownerUid":"<ownerUid>"}`. | `201`; `{reportId,status:"pending",confirmAfter}`. | `users/{ownerUid}/deathReports/{reportId}` has pending status, submitter beneficiary UID, and `confirmAfter`; activity event `deathReportSubmitted` exists. Pass if eligible beneficiary creates one pending report. |
| 22. Delayed automatic confirmation fires | No HTTP mutation. Wait until `confirmAfter` plus several seconds. Poll `GET /legacy/status/<ownerUid>` using `<beneficiaryToken>` to observe request status; inspect report/owner via privileged Firestore tooling. | Status route: `200`; request state has status `released`. There is no HTTP route that returns death-report confirmation status. | Report becomes confirmed with `confirmedAt`; owner has `deceased:true` and `deathConfirmedAt`; active policy is frozen; active grants become released. Pending/denied grants remain unchanged. Pass only when these states appear after the configured delay. |
| 23. Released legacy access follows frozen policy | After step 22, request permitted family and denied private entry via `GET /entries/<id>?ownerUid=<ownerUid>&access=full`, then ask AI again. | Allowed family route returns `accessGranted:true`; private route remains a safe denial. AI `201` success selects only policy-permitted entries and returns citations. | Grant is `released`; frozen policy is used for released access. Pass if release does not bypass the policy, hidden-entry, or release-date checks. |
| 24. Release-date-gated entry becomes available only after date | Before `releaseDate`, request the future entry; after the date has passed on backend/server time, repeat the same request. | Before: `200` denial `{accessGranted:false,message:"Entry is not available yet."}`. On/after date: eligible projection can return `accessGranted:true` if policy permits. | Entry `releaseDate` remains unchanged. Pass if it is denied before and permitted only at/after the date; AI selected IDs likewise exclude it before release. |
| 25. Cross-user access denial stays privacy-safe | Use `<intruderToken>` against an existing owner's entry and a random/nonexistent entry: `GET /entries/<entryId>?ownerUid=<ownerUid>&access=full`. | `200` safe refusal object `{accessGranted:false,message}`. Current refusal text can vary by reason; do not assert identical message for missing, policy-denied, hidden, or date-gated entries. | No title, content, summary, tags, or owner-only fields are present. Pass if response shape indicates denial without revealing private record data or whether a specific record exists. |

## CORS, Swagger, Firebase documentation, and URL checks

| Check | Request / source | Expected result |
|---|---|---|
| Allowed CORS preflight | `OPTIONS <baseUrl>/entries` with `Origin: http://localhost:8081`, `Access-Control-Request-Method: POST`, `Access-Control-Request-Headers: authorization,content-type` (repeat with `http://localhost:19006` when used). | Preflight succeeds (normally 204) and returns exact `Access-Control-Allow-Origin`, allowed methods, and Authorization/Content-Type headers. |
| Unauthorized origin | Same preflight with an origin absent from `CORS_ALLOWED_ORIGINS`, e.g. `http://localhost:9999`. | Response has no `Access-Control-Allow-Origin` for that origin; browser cannot read API response. Do not use wildcard CORS in production. |
| Swagger UI | `GET <baseUrl>/api` | `200`, Swagger UI loads. Use its Authorize control with a test Firebase ID token to try a protected endpoint. |
| OpenAPI JSON | `GET <baseUrl>/api-json` | `200`, valid OpenAPI JSON. `components.securitySchemes.bearer` is HTTP bearer/JWT and protected routes show security requirements. |
| Firebase Web configuration docs | Review [FRONTEND_INTEGRATION.md](./FRONTEND_INTEGRATION.md), Firebase Console Web App configuration, and frontend environment configuration. | `apiKey`, `authDomain`, `projectId`, `storageBucket`, `messagingSenderId`, and `appId` are documented as frontend client config; actual project values are obtained from Firebase Console, not backend source. |
| Expo web base URL | `EXPO_PUBLIC_API_BASE_URL=http://localhost:3000` for local same-computer development; frontend browser **origin** is separately allowlisted. | Browser requests reach API and pass CORS only when its actual origin is allowlisted. |
| Android emulator base URL | `http://10.0.2.2:3000` (or configured port). | Emulator reaches the host computer's backend. |
| Physical device base URL | `http://<backend-computer-LAN-IPv4>:3000` on same reachable LAN, subject to firewall. | Device reaches backend; Expo native requests do not use browser CORS. |
| Production base URL | `https://<production-backend-host>`; no production URL is configured in this repository. | Frontend receives deployment URL out-of-band; HTTPS and explicit allowed origins are configured. |

## Existing automated coverage and boundaries

The manual plan complements, rather than duplicates, the current tests. Existing `test/people-integration.test.ts` covers invitations, join, policy-gated entry/AI access, revoke/freeze behavior, and privacy-safe denials with a mocked test UID. `test/legacy-integration.test.ts` covers request transitions and actor authorization. `test/death-report.integration.test.ts` covers eligibility, duplicate/self reports, delayed confirmation, policy freeze, active-grant release, and released access. `test/hash-chain.integration.test.ts` covers publish sequence/hash behavior. `test/firestore-rules.emulator.test.ts` verifies direct client reads/writes are denied where intended. These emulator tests mock Firebase token verification and Gemini; they do not prove the real frontend Firebase sign-in flow or real Gemini output.

No new automated test was added: the existing emulator tests already cover the lifecycle and policy gates, while real ID-token sign-in requires project credentials and the presentation flow needs user-provided Firebase Web configuration. The HTTP checklist is the manual end-to-end layer for those integration boundaries.

## Known integration gaps / interpretation

- The repository does not contain the actual Expo frontend origin, production API URL, Firebase Web App values, or a real test-account specification. Obtain them from the frontend/project owner before a shared-environment run.
- `/legacy/status/:ownerUid` exposes request status, not death-report status. Verify death report and owner transition with authorized Firestore tooling; do not add direct beneficiary Firestore reads.
- `POST /auth/join` invalid/expired/used-code outcomes are service-level `{error:...}` bodies and may still use HTTP 201; the frontend must inspect response fields as well as status.
- AI returns HTTP 201 for success, denial, and provider-error result bodies. Inspect `status` and `error.code`; do not infer AI success from HTTP status alone.
- Published entries are append-only and cannot be edited. Create separate fixture entries for family/private/future cases rather than trying to modify one after publication.
- Death report requires a beneficiary grant in `active` or `released` state. After verifying revocation, renew via a new request and owner approval/activation before continuing the death-report segment.
- Direct client reads are owner-only for profile/entries where allowed, and all client writes are denied by rules; beneficiary projections are API-only.
